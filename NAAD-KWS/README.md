# NAAD-KWS

Ultra-lightweight, open-source keyword spotting for ESP32, built for
**SIH PS-172**: edge wake-word detection + low-latency hand-off to a cloud
ASR server.

## Why this isn't built on `espressif/esp-sr`'s WakeNet

`esp-sr`'s WakeNet models ("Hi ESP", "Alexa", etc.) are Espressif's own
pretrained, closed-training-pipeline wake-word models — new custom keywords
have to be submitted to Espressif's commercial "custom wake word" service.
That conflicts directly with two constraints in the problem statement:

* *"No pre-trained global keywords... teams need to train on a custom
  keyword"*
* *"Proprietary, closed-source, or commercial voice-activation SDKs...
  strictly prohibited"*

So this project trains its **own** tiny model from scratch on **your**
"naad" recordings, using only open frameworks (TensorFlow / TensorFlow
Lite for Microcontrollers) and open ESP-IDF components (`esp-tflite-micro`,
`esp-dsp` — both Apache-2.0/MIT, used only for generic FFT/tensor-op
primitives, not for the keyword model itself). `esp-sr`'s AFE (acoustic
front-end: AGC/noise-suppression) can optionally be added later as a
pre-processing stage since it's a signal-processing component, not a
pretrained wake-word model — see "Optional hardening" below.

## Architecture

```
 ESP32 + I2S mic                                    Cloud
┌─────────────────────────────────────────┐        ┌────────────┐
│ I2S DMA → ring buffer (audio_capture.c)  │        │            │
│        │ 20ms hops                       │        │  ASR       │
│        ▼                                 │        │  engine    │
│ MFCC (mfcc.c) → 49×13 sliding window     │        │ (Whisper / │
│        │                                 │        │  Vosk /    │
│        ▼                                 │        │  cloud API)│
│ int8 DS-CNN (kws_model.cc, TFLite-Micro) │        │            │
│        │ p(naad)                         │        └─────▲──────┘
│        ▼                                 │              │
│ debounce (3 consecutive windows)         │   raw PCM,   │
│        │ trigger                         │   pre-opened │
│        ▼                                 │   TCP socket │
│ network_stream.c ─────────────────────────────────────┘
└─────────────────────────────────────────┘
```

The TCP socket to the ASR server is opened **once at boot** and kept alive
(`network_stream.c`), so the only latency between "keyword ends" and
"cloud ASR receiving audio" is a `send()` syscall — no DNS lookup, no TCP
handshake, no TLS negotiation on the hot path. `main.c` logs that exact
delta (`Keyword-end -> stream-sent latency`) so you can report it as a
number in your evaluation.

## Quick start

### 1. Collect data
You said you'll upload the dataset — drop wavs into:
* `dataset/naad/` — the keyword, spoken many times, by multiple people,
  distances, and background conditions. Aim for 200–500+ clips; more is
  always better for a low false-accept rate.
* `dataset/negative/` — other words/phrases, silence, ambient talk. Include
  words that sound *similar* to your keyword — those are what actually
  cause false accepts.
* `dataset/negative/background_noise/` — a handful of longer (5–30s) room
  noise / traffic / fan noise clips, used only for augmentation (mixed into
  both classes at random SNR), not as standalone training examples.

No strict length requirement — `load_wav()` in `audio_utils.py` pads or
center-crops everything to 1.0s automatically. (If you don't have data yet,
`python training/record_samples.py --label naad --count 50` records from
your laptop mic.)

### 2. Train
```bash
cd training
pip install -r requirements.txt --break-system-packages
python train.py
```
Prints held-out accuracy, a confusion matrix, and an estimated false-accept
rate. `training/artifacts/training_history.png` shows the learning curves.

### 3. Quantize + generate ESP32 sources
```bash
python convert.py
```
Writes `training/artifacts/naad_kws_int8.tflite` **and** overwrites
`esp32/naad_kws/main/model_data.h` / `model_data.cc` with your trained
model, ready to compile straight into firmware.

After this step, copy the printed `mean`/`std` values (also saved in
`training/artifacts/feature_{mean,std}.npy`) into
`esp32/naad_kws/main/mfcc.h`'s `MFCC_FEATURE_MEAN` / `MFCC_FEATURE_STD`
defines — the on-device normalization must match training exactly.

### 4. Evaluate properly
```bash
python test_model.py            # held-out split
python test_model.py --all      # full dataset, quick smoke test
```
Reports the exact metrics the problem statement asks for: true-positive
rate, false-accept rate, model size, and inference latency.

### 5. Build & flash the ESP32 firmware
Requires [ESP-IDF v5.x](https://docs.espressif.com/projects/esp-idf/en/latest/esp32/get-started/).
```bash
cd ../esp32/naad_kws
idf.py set-target esp32
idf.py menuconfig     # under "NAAD-KWS Configuration": set WiFi SSID/password,
                       # ASR server IP/port, detection threshold, hangover, stream length
idf.py build flash monitor
```
Before building, wire an I2S digital mic (e.g. INMP441): `WS`→GPIO25,
`SCK`→GPIO26, `SD`→GPIO22, `L/R`→GND, `VDD`→3.3V (edit the pins in
`audio_capture.h` if your wiring differs).

### 6. Try the end-to-end demo
```bash
python asr_server_reference.py --port 5005
```
Speak the keyword near the ESP32 — you should see `KEYWORD DETECTED` in
`idf.py monitor`, and a `received_utterances/utterance_000N.wav` appear on
the server side within milliseconds.

## Memory / CPU budget vs. the <256KB RAM, <10% idle-CPU requirement

| Component                          | Approx. footprint |
|-------------------------------------|-------------------|
| TFLite-Micro tensor arena            | 40 KB (static)     |
| Audio ring buffer                    | ~48 KB             |
| int8 model (flash, not RAM)          | typically 10–30 KB depending on final architecture |
| I2S DMA buffers, WiFi/lwIP stacks, task stacks | a few tens of KB (standard ESP-IDF overhead, not specific to this app) |
| **Total app RAM**                    | comfortably under 256 KB, even before ESP-IDF's own baseline usage |

CPU: the model runs **5 inferences/second** (`STREAM_HOP_MS = 200`), each a
few tens of thousands of MACs for a 2-layer depthwise-separable CNN —
sub-millisecond to low-single-digit milliseconds per `Invoke()` on the
ESP32's Xtensa core, i.e. comfortably under 10% duty cycle while idling.
Exact numbers depend on final trained architecture size — `test_model.py`
prints a PC-side latency figure as a sanity check, and `main.c` logs the
real on-device `Invoke()` time via `esp_timer` so you can report a measured
(not estimated) number for evaluation.

## Design notes / known simplifications to tighten before a hardware demo

* **Overlap-add in `main.c`**: the sliding window currently calls
  `mfcc_compute_frame()` on a 20ms hop directly, but MFCC frames are
  defined over a 30ms window. In production, keep a small 10ms carry-over
  buffer between hops and feed `mfcc_compute_frame()` the combined 30ms
  window. Flagged clearly in a comment in `main.c`.
* **VAD-based stream length**: `main.c` streams a fixed
  `NAAD_STREAM_SECONDS` window after trigger. For production, add a simple
  energy-based voice-activity detector so streaming stops as soon as the
  user finishes speaking, cutting bandwidth and ASR latency further.
* **Optional hardening**: if false accepts are still too high after more
  data, esp-sr's **AFE** (acoustic front-end — AGC + noise suppression,
  not a wake-word model) can sit between the mic and `mfcc.c` as a
  pure signal-processing stage without reintroducing the proprietary
  wake-word issue this project avoids.
